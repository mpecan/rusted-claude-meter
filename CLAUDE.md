Rusted Claude Meter is a Tauri v2 tray app (macOS + Linux) showing Claude plan usage — a port of the SwiftUI ClaudeMeter.

Layout: `crates/meter-core` = pure domain (no I/O); `crates/meter-api` = claude.ai HTTP client + response mapping; `crates/meter-files` = on-disk contracts (the atomic-write idiom, `~/.claudemeter/`, the Claude Code status-line bridge); `crates/meter-render` = pure tray-icon rendering (`IconState` → SVG → RGBA, no platform code); `src-tauri` = app shell (tray, scheduler, storage, notifications) **plus both binaries**; `src/` = vanilla TS frontend.

**Two binaries, one package (issue #72).** `rusted-claude-meter` is the GUI; `rusted-claude-meter-statusline` is the Claude Code bridge, built from `src-tauri/src/bin/statusline.rs` against `meter-files` and nothing else, so it links **none** of AppKit/WebKit/Carbon/CloudKit/QuartzCore. That is the whole reason `meter-files` is a crate rather than a module of `src-tauri`: Claude Code spawns `statusLine.command` on every status-line redraw, several times a second, and mapping the GUI's frameworks cost ~3ms of a ~5.3ms invocation — more than the bridge's own work — for frameworks it never touches. Measured on the shipped `.app` bundle, both doing the full job (read stdin, write the recording): 5.3ms → 2.8ms, against 2.1ms for `/usr/bin/true` — so what is left above the floor is the bridge's own work. **Both `[[bin]]` targets are declared explicitly** in `src-tauri/Cargo.toml`: `tauri-cli` picks the bundle's main binary by matching a target name against the package name, and its "if there is exactly one, that is it" fallback stops firing at two, so with both inferred neither would be main and the bundler would have nothing to build the `.app` around. Packaging then needs **no configuration at all** — `tauri-bundler` copies every `[[bin]]` into `Contents/MacOS/` (macOS, and into `sign_paths`, so it is codesigned and notarized with the app) and into `usr/bin/` for the `.deb`, which the AppImage and `packaging/aur/PKGBUILD` are both built from. `externalBin` is *not* used and would be the wrong tool. Which binary a new setup is pointed at is resolved at runtime by `statusline::setup::invocation_for`, which probes for `BRIDGE_BIN` beside `current_exe()` — one code path that picks the fast binary from an `.app`, a `.deb` and a `cargo run` target dir alike, and degrades to the subcommand rather than writing a path to nothing. `BRIDGE_BIN` is mirrored in that second `[[bin]]`'s name; rename them together. **The `rusted-claude-meter statusline` subcommand stays a working alias indefinitely** — it lives in the user's `~/.claude/settings.json`, which this app never edits. `bridge::parse_flags` is the shared half so the two entry points cannot drift. The load-bearing proof is `src-tauri/tests/statusline_bridge.rs::the_bridge_binary_links_nothing_from_the_gui` — nothing in the *source* says "do not link Tauri", and one `use rusted_claude_meter_lib::…` would put it all back and still pass every unit test — paired with `the_gui_binary_does_link_them` so it cannot pass vacuously.

**Terms-of-Service consent gate — the app makes no claude.ai request until the user opts in.** Polling an internal, undocumented claude.ai endpoint with the user's session cookie and browser-shaped headers is, on a plain reading, prohibited by Anthropic's Consumer Terms §3 ("automated or non-human means"); `docs/terms-of-service.md` is the cited write-up and the thing every surface links to. `AppSettings::tos_acknowledged` defaults **false** — including for installs upgrading from a build that predates it, which is the point, not an oversight — and `consent::ConsentGate` (a `sync::AtomicFlag` alias, seeded in `lib.rs`, flipped by `commands::consent::set_tos_acknowledged`) is its runtime mirror. Three paths could reach claude.ai and all three check it: the scheduler transport (`LiveTransport::attempt`, checked *before* the credential store so a withholding user gets no keychain prompt either), `commands::set_session_key`, and `commands::browser::import_browser_session`. A closed gate parks the loop in `Phase::AwaitingConsent` with `next_delay() == None` — no polling at all, not slower polling. Never make the gate default-open, and never let a transport be built without one: `LiveTransport::with_base_url` starts **closed** on purpose, so a wiring mistake costs a visibly dead meter rather than silent un-consented traffic. Copy for both surfaces lives once in `src/tos-notice.ts` (wizard consent step + Settings section), and the wizard's `consent` step sits *before* `session` so the risk is accepted before a credential is requested. **The wizard picks the usage source first (issue #71)** — `src/wizard-view-model.ts::wizardSteps(source)` returns one of two paths, branching on `tosAppliesTo` rather than a second reading of the same fact, and `consent`/`session`/`validate` exist only on the claude.ai one. The step indicator counts the path actually being walked, so the Claude Code branch says "of 5" instead of promising steps it never shows; `nextStep`/`previousStep` are how `wizard.ts` moves, so no button names its neighbour. `tosStateHint` takes `applies` as well as `acknowledged` because on the status-line source *both* of the other hints are wrong in opposite directions — "Tracking is paused" describes a dead meter to someone whose meter works, and "Tracking is on" implies consent never given.

**Usage source — claude.ai or Claude Code, chosen explicitly, never blended.** `AppSettings::usage_source` (`source::UsageSource`, default `ClaudeAi` so an upgrading install stays on the source it already had) picks where the scheduler fetches from. `ClaudeCodeStatusline` reads `~/.claudemeter/statusline.json`, written by the `rusted-claude-meter-statusline` bridge (or the GUI binary's `statusline` alias) that Claude Code invokes as its `statusLine.command`; because Claude Code derives those numbers from `anthropic-ratelimit-unified-*` response headers on the user's own traffic, that path **originates no claude.ai request and so is deliberately not consent-gated** — `lib.rs` only parks on withheld consent when the source is claude.ai, or a user who declined would be stranded on a source that needs no permission. The two are a trade, not a fallback chain: the status-line source reports the headline windows only (no scoped models, no spend) and updates only while Claude Code runs, so auto-failover would leave the tray unable to say how old a number is or which limits it covers. `source::SourceSelection` (an `AtomicFlag` alias; construct with `selection`, read with `selected`, write with `select` — all in terms of `UsageSource`, so the bool is an implementation detail of those three) is the **one** runtime mirror, shared by `scheduler::SourcedTransport` and `SchedulerCore` and read **every tick**, so the Settings picker takes effect on the next poll without the loop being rebuilt; consent stays checked inside `LiveTransport::attempt` alone, so routing to the status line bypasses it by construction rather than by an added exception. **Both gates now sit on `signin::SessionSink` too** (`consent` *and* `source`, checked in that struct's order — source first, because "you need no key" is the useful answer to someone on the Claude Code source): validating a pasted or imported key is itself a claude.ai request, so `commands::session::set_session_key` and `commands::browser::import_browser_session` refuse with `WrongSource` before touching the credential store. `SourcedTransport`'s dispatch plus `store_and_validate`'s two checks account for every line in the app that can reach claude.ai. The load-bearing proof is `sourced.rs::the_statusline_source_puts_nothing_on_the_wire_at_all` — a healthy wiremock server, valid key, open gate, and `received_requests()` empty — paired with `the_claude_ai_source_does_reach_the_very_same_server` so it cannot pass vacuously. A missing/corrupt/window-less file is `FetchOutcome::AwaitingStatusline` → `Phase::AwaitingStatusline`, which unlike the other waiting phases **keeps polling** (nothing else signals that Claude Code has since run) and never accumulates backoff. The file's `recorded_at` becomes the snapshot's `fetched_at`, so the existing staleness rule ages it with no special-casing. **The core paces itself to what a fetch costs**, so it holds `Arc<SourceSelection>` — the same handle the transport dispatches on, not a second copy it must be told about: `poll_interval()` uses `UsageSource::fixed_poll_interval()` (15s for the status line) instead of the user's `RefreshInterval` — that setting paces *claude.ai requests*, and there are none — and `should_fetch` skips the 55s `MEMORY_TTL` unless `reaches_claude_ai()`. Those two are the only policy questions on `UsageSource`, both exhaustive `match`es so a third source is a compile error at each: `reaches_claude_ai()` is the single fact the consent gate, the session-key refusal and the TTL all follow from; cadence stays separate because "how expensive is a fetch" and "does it leave this machine" could differ. `RefreshInterval` still drives `staleness()` on both sources. `run_loop` writes the cache and the `usage.json` export only when `core.is_new_snapshot()`, or the fast cadence would rewrite both files four times a minute with identical bytes. `interval`/`source` are **public fields** rather than setters: they are inputs pushed in, everything derived stays private, and two one-line setters were the same code twice. Two files live in `~/.claudemeter/` and flow opposite ways — `usage.json` out (`meter_files::export`), `statusline.json` in (`meter_files::statusline`) — which is why they are separate modules and separate paths. `statusline/mod.rs` owns the file contract (payload, path, `record`, `read`), `statusline/bridge.rs` owns Claude Code's payload (argv, blob parsing, render, `execute`); `main.rs` dispatches via `lib::run_cli` before any Tauri init, so the alias never builds an app either. Claude Code **2.1.216+** only — older builds emit no `rate_limits`, and a Rusted Claude Meter predating the subcommand treats `statusline` as an unknown arg and launches the GUI. `used_percentage` arrives as a JSON **integer** on round numbers (`3`, not `3.0`): fixture `crates/meter-files/tests/fixtures/statusline_payload_live.json` is captured verbatim and is the thing to check shape questions against. Setup is a `/statusline` invocation: the agent behind Claude Code's `/statusline` has **Read and Edit only** — it cannot run the binary to learn the binary's path — so `statusline::setup` writes `~/.claudemeter/statusline-command.txt` on every launch (the exe can move) holding this machine's command plus merge instructions, and `src/usage-source.ts::STATUSLINE_SLASH_COMMAND` is the sentence that points the agent at it. That filename is mirrored across `setup::SETUP_FILE` and that constant — rename them together. All three `~/.claudemeter/` paths go through one `meter_files::export::claudemeter_path(home, file)` helper; per-file wrappers were the same one-liner three times and tripped the duplication ratchet. The bridge's `--pace` flag appends the off-pace signal (`5h 95% · 7d 40% · 🔥1.6×`): display is the flag's business because the status line is its own surface (same reasoning as `tray::PaceOptions`), but the *maths* comes from `~/.claudemeter/statusline-config.json`, published by the `SettingsState::mirroring_with` callback on install and after **every** settings write (a callback, not a path — the settings store has no business knowing a consumer's file format, and `lib.rs` supplies what to mirror) — `weekly_pace_days` is a denominator, not a preference — and the same 75% weekly usage is `🔥1.3×` over 7 days and silent over 5. **The pace defaults live in `meter_core::pacing`** (`DEFAULT_WEEKLY_PACE_DAYS`, `DEFAULT_PACE_TRACKING_ENABLED`, `clamp_weekly_pace_days`; the `WEEKLY_PACE_DAYS` range itself is private behind the clamp) because `AppSettings` and the bridge's mirror have to agree and neither crate can see the other — the mirror is what the bridge falls back to before the app has ever written one, so a second opinion is the tray and the status line quoting different ratios for the same usage. Sharing the values makes that a compile-time impossibility; an earlier cross-crate test asserting the two agreed was the same fact enforced by watching, and went when the constants were lifted. `pace_tracking_enabled` is the master switch and vetoes the flag. The status line raises overuse to `HEAVY_OVERUSE_THRESHOLD` (1.2) rather than `RISK_THRESHOLD` (1.0) the tray uses: a permanent prompt with no expected-% context would otherwise flicker a flame in and out and render `🔥1.0×`. `statusline::home_path(file)` is the one `$HOME` resolver (callers name the file) — a `default_path` in both `statusline` and `config` differed by one `use` and the bridge called the wrong one, silently reading the recording as its config. `meter_files::io::read_json` / `write_json_pretty` are the shared halves of the on-disk idiom (`cache.rs`/`settings.rs` stay in `src-tauri` despite using it: they write into Tauri's app data dir, which only an `App` can resolve) — `read_json` for cache/settings/config/statusline, `write_json_pretty` for the three files published for something else to read (`usage.json`, the recorded reading, the config mirror). User copy lives once in `src/usage-source.ts` (the Settings block itself is `src/statusline-setup.ts`, split out to keep `settings-view.ts` under the 700-line hard gate); user-facing guide is `docs/claude-code-statusline.md`.

Run `just check` before considering any change done — it is what CI enforces: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings` (pedantic + nursery on; `unwrap_used`/`expect_used`/`panic`/`todo` are deny), `cargo test --workspace`, the 500/700-line file-size gate, `cargo deny check` (licenses/advisories/bans/sources, `deny.toml`), `cargo dupes check` (structural duplication ceiling), `cargo llvm-cov` (coverage floor), and the frontend (`tsc --noEmit` + `npm run test`). Test modules may `#![allow(clippy::unwrap_used)]`. CI runs on Linux only (`.github/workflows/ci.yml`) — the macOS test/clippy leg was dropped on purpose (the app is developed on macOS, and macOS runners cost 10x the minutes), so the `#[cfg(target_os = "macos")]` surface (popover, tray click handling) is held to the same `-D warnings`/test gate *only* by running `just check` locally on a Mac; a Linux-only check (CI or a Linux container) never compiles it. `just check` also lints the **lite** build (`lint-lite`: `--no-default-features`, browser import and `rookie` compiled out) — a parameter used only inside a `#[cfg(feature = "browser-import")]` block otherwise passes the default-feature clippy and fails CI. One CI-only check still has no local `just` recipe: actionlint over `.github/workflows/*.yml`.

Quality gates in `justfile`/`ci.yml` are ratchets: the coverage floor (`coverage_min_*`) only ever goes up, the duplication ceiling (`dupes_max_*`) only ever goes down. Never loosen either to make a change pass — add tests or remove the duplication instead. `deny.toml`'s `[advisories] ignore` list holds only pre-existing "unmaintained" transitive notices with no safe upgrade (tauri/gtk-rs tree); don't add a new entry there without checking whether the flagged crate is a real, fixable dependency of ours first.

The frontend must be built once (`npm run build`) before any cargo command touching `src-tauri` — `tauri-build` requires `dist/` to exist.

Model-scoped limits contract: the API's `limits` array is the source of truth for per-model caps; entries are keyed by `scope.model.display_name` (API-supplied, e.g. "Sonnet", "Fable"), headline kinds (`five_hour`/`seven_day` and the live payload's `session`/`weekly_all`) are excluded from the scoped pass, and incomplete entries are skipped, never errors. Flat fields are the headline fallback. **`is_active` is not a display gate** — a captured live response reports it `false` on every weekly entry, the scoped ones *and* the `weekly_all` that claude.ai itself displays, so it marks the currently-binding window; `ScopedLimit::is_visible` and `buildViewModel` gate on the user's `shown_scoped_models` opt-in alone (gating on `is_active` too made every weekly scoped model unshowable, fixed after 0.1.4). Fixtures: `crates/meter-api/tests/fixtures/usage_response.json` (hand-written, covers every branch) and `usage_response_live.json` (captured verbatim — the one to check shape questions against).

Pace-tracking contract (issue #16): pace ratio, `PaceBand`, projections and the hybrid `pace_signal` live in `meter_core::pacing`/`snapshot` and MUST stay numerically identical to `src/pacing.ts` (both file headers promise this — change them together). Ratio = `min(utilization,100) / expected%`, where expected is the elapsed fraction of the *pacing span* capped at 1.0; `None` under `MIN_ELAPSED_FRACTION` (5%) elapsed, but the limit-hit projection bypasses that grace while honouring the 5%-utilization floor. `pace_tracking_enabled` (default true) is the master switch — when off the popover computes no pace at all (ratio/expected/projection all null, quota-first only) and the tray shows no pace anywhere; `weekly_pace_days` (5–7, clamped) and `pace_first_display` are the two configurable sub-settings under it. The tray carries both flags separately (`tray::PaceOptions`, built once by `tray::pace_options`): `pace_first_display` gates the **icon** only (via `PaceOptions::icon_is_pace_first`, which ands in the master switch), while the **menu**'s per-window detail lines honour `pace_tracking_enabled` alone. Do not re-fold them — the menu is the whole Linux surface, so gating it on an icon preference hides pace from anyone who never finds that toggle. `pace_signal` is headline-only (session + weekly, never scoped) and hybrid: overuse on either window, underuse only on weekly. In pace-first display the tray icon's primary metric always becomes a ratio (`pace_signal.ratio ?? session.pace_ratio ?? weekly.pace_ratio`, its band drives the colour), but the flame/snowflake badge is gated on the hybrid signal being present; the popover's per-card pace ratio/projection is always computed regardless of the toggle. `PaceSignal::tooltip()` is upstream-parity API with no caller since the tray menu stopped rendering a headline pace line — keep it and its pinned strings.

Tray: `tray/mod.rs` decides *what* to show (icon state, menu lines, the `TrayDiff` debounce); `tray/native.rs` owns the Tauri `TrayIconBuilder` handles and pushes it. Split for the file-size gate and to keep that boundary sharp, not because there is a second backend.

Linux surface — deliberate, after evaluating the alternatives. The tray **menu** is the whole Linux surface, so it carries as much as a menu usefully can: a status line, then per usage window (5-hour, 7-day, each opted-in scoped model) a `label: N% — resets in …` line plus an indented `2.1× pace · 40% expected · hits limit ~1:59 PM` detail line (`tray::model::detail_line`, suppressed only while the window has neither enough elapsed time nor enough usage for a meaningful ratio). Its first two segments are exactly the popover's own pace line, so the surfaces read alike. There is deliberately **no** separate headline pace line: `PaceSignal::tooltip()` said the same thing in one much wider string, and menu width is a real cost when the menu is the whole surface. The detail line is the only tray text with a wall clock in it: the zone is resolved once at `tray::init` and threaded through `MenuOptions` rather than read per tick, which also keeps the specs deterministic. "Open Rusted Claude Meter" opens the main window as an ordinary window — `tauri.linux.conf.json` (auto-merged per target by Tauri) overrides the `main` window to be opaque and resizable there, since `transparent` is creation-time and macOS needs it true for the `NSPopover`. There is no Linux popover, and adding one is not a small change: libappindicator (what `tray-icon` uses) omits SNI's `Activate`, so no click reaches the app; owning the item via `ksni` supplies `Activate` but costs GNOME ~400ms on every menu open (its AppIndicator extension waits out the double-click timeout whenever the method merely *exists*), and Wayland forbids a client positioning its own toplevel at all (`set_position` and `always_on_top` are documented no-ops there), so an anchored pop-down cannot be implemented by an application. A shell-owned popup needs a GNOME Shell extension or a Plasma plasmoid, which is a separate project rather than a change to this one. KDE also renders tray icons into a **square** cell (`AbstractItem.qml` pins `implicitWidth` to `itemSize`; `Kirigami.Icon` preserves aspect), so the 66x22 gauge draws at a third of panel height there. Accepted, and surfaced rather than documented-and-forgotten: Settings shows a hint under the icon picker on Plasma offering the near-square styles, driven by `settings-view-model.ts::squareTrayHint` — which derives "near-square" from each preview's own dimensions (`height / width >= 0.8`) rather than a hardcoded style list, so a new style cannot leave it stale. `meter_core::LinuxDesktop` classifies `XDG_CURRENT_DESKTOP` for both this and the GNOME extension hint; one `linux_desktop` command, not a boolean per desktop. User-facing write-up with screenshots: `docs/linux.md`, regenerated from the container harness by `just linux-screenshots`.

The macOS popover is a native `NSPopover` hosting the webview (via the macOS-only `tauri-plugin-nspopover`, git dep pinned in `src-tauri/Cargo.toml` and allow-listed in `deny.toml`); it's `#[cfg(target_os = "macos")]`-gated so Linux still builds, where the same window is opened from the tray menu instead. `commands/popover.rs::set_popover_height` content-fits the macOS popover on every measurement; on Linux it fits the window **once per show** (the `ContentFit` latch, armed by `show_main_window`), because that window is user-resizable and the frontend re-measures on every broadcast — applying every measurement would undo a manual resize within a minute. Settings is a separate window; the popover renders one of two layouts (`popover_layout`: rows/cards) with status colours keyed to the user's warning/critical thresholds.
